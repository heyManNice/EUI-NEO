# 核心审计（Core Audit）

这份文档回答一个问题：**`core/` 现在难维护在哪里**，以及按什么顺序动它最小、最值。

它不重复 `docs/工具协议.md` 的内容——工具协议规范了框架如何为诊断工具提供能力，核心运行时保持零工具门控、零工具策略、Release 零工具符号。本审计聚焦于工具接缝之外的核心本身。

## 一、度量

| 指标                 | 数值                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------- |
| 规模                 | 35,256 行 / 92 个文件                                                                    |
| 体量分布             | `core/render` 19,695（56%）、`core/runtime` 4,615、`core/app` 2,356、`core/platform` 2,212、`core/tooling` 1,055、`core/window` 1,036、`core/input` 625、`core/audio` 217 |
| 最大的文件           | `render/text.cpp` 1,978、`dsl.h` 1,939、`vulkan/vulkan_shadertoy.cpp` 1,466、`vulkan/vulkan_backend.cpp` 1,457、`render/image_source.cpp` 1,233、`runtime/runtime_render.h` 1,185、`runtime/runtime_update.h` 1,120 |
| 条件编译             | 0 处特性开关。只剩平台宏（`_WIN32` 24 处）与 `EUI_APP_RUNNER_LIBRARY` 2 处              |
| 工具门控             | 判定 1 处（`core/tooling/config.h`）+ 2 处开发便利（`app_runner.h`、`include/eui/dsl_app.h`） |
| `Runtime` 公共方法   | 76 个（一个类，跨 10 个 runtime 头 / 4,615 行）                                          |
| 内部头被框架外引用   | 66 处（`components` 51、`modules` 14、`examples` 1；`apps` 0）                           |

## 二、发现（按价值排序）

### F1 公共面与内部面没有目录界限（最值）

**现象**：`include/eui/*` 已经是一层转发/别名（`eui/dsl.h` 里 `using Ui = core::dsl::Ui;`），但框架内部有 **66 处**直接 `#include "core/…"`，其中 **46 处是 `core/dsl.h`**——而 `eui/dsl.h` 本来就是为它准备的。

**证据**：

```bash
grep -rn '#include "core/' components modules apps examples | wc -l     # 66
grep -rh '#include "core/[^"]*"' components modules apps examples | sed -E 's/.*"(.*)"/\1/' | sort | uniq -c | sort -rn
#   46 core/dsl.h   6 core/render/text.h   3 core/platform/platform.h   2 core/tooling/model.h
#    2 core/render/primitive.h   1 core/window/window_backend.h   1 core/tooling/pass.h
#    1 core/runtime/runtime_geometry.h   1 core/render/render_types.h   1 core/render/render_backend.h
#    1 core/dsl_runtime.h   1 core/app/performance_snapshot.h
```

**维护成本**：从路径看不出"这个头是对外承诺还是内部实现"，所以**任何一次内部重构都要人工判断会不会破坏使用者**。这不是编译问题（`core/` 会被安装），是**可判断性**问题——维护成本里最贵的那一类。

**建议分两步，第一步零风险**：

1. **A1 机械替换**：`components/`、`modules/` 该用 `eui/*` 的地方改成公开路径；`eui/` 缺哪个补哪个转发头（`text.h`、`platform.h` 已有 `eui/platform.h`、`tooling.h`）。
2. **A2 落一条可自动检查的约定**：框架外目录里 `#include "core/` 必须为 0（`apps/` 现在就是 0，说明这条约定可执行）。

**验收**：`grep -rn '#include "core/' components modules apps examples | wc -l` 为 0；行为不变（只换包含路径）。

**注意**：这一步只动"包含路径"，**不动名字**（`core::dsl::Ui` 这类限定名迁移是另一个量级的工作，值与不值取决于是否要把 `eui/*` 提升为受版本约束的公共 API——这是维护者要拍板的决定，不属本次审计）。

### F2 `Runtime` 一个类 76 个公共方法

**现象**：职责**在文件层**已经分好了（`runtime_lifecycle.h` / `runtime_input.h` / `runtime_render.h` / `runtime_update.h` + `core/tooling/*`），但**在类层**没有分：全部是 `Runtime::` 的成员，改一个功能要通读 414 行的类定义 + 10 个头。

**维护成本**：中等。带来的实际困扰是"找不到方法在哪"和"改一个域要读整张表"，而不是编译或耦合问题。

**建议**：先做**零风险的一半**——按域排序并加分节注释（生命周期 / 输入 / 渲染 / 更新 / 工具 / 查询），并在类头写明"新增方法放在哪个域"。若之后仍痛，再考虑把某一域（最可能是工具查询）收成独立的视图对象。**不建议**为它引入接口继承或多级基类：那份间接换不来多少。

**验收**：`core/dsl_runtime.h` 里出现分节注释；方法顺序与域一致；无行为改动。

### F3 `core/dsl.h` 1,939 行混了五个东西

`Element`（94）、`StateStore`（246）、`BuilderBase`（303，约 530 行 CRTP）、`ShapeBuilderBase`（837）、`LayoutBuilder`（1037）+ `Ui`。

**维护成本**：中等偏低——它稳定、改动少，热点不在它。真正的成本是"读一个构建器要滚过整个头"。

**建议**：**看痛点再动**。要动就按 `element.h` / `builder.h` / `ui.h` 拆，但这是公共头拆分的动作，收益低于 F1，风险高于 F1，不该先做。

### F4 `core/render/text.cpp` 1,978 行

字体加载 / 图集 / 排版（含 ink-box 居中）/ 绘制在一个文件里，是核心最大的源文件。

**维护成本**：中低。上次改动（sharp DPI、emoji 度量、wrap-content 测量）都落在它，说明它是"会持续被改的文件"。

**建议**：等下一次确实要改它时顺手拆（`face/atlas/layout`），不要为拆而拆。

### F5 条件编译约束已收敛

核心只剩平台宏与 2 处 `EUI_APP_RUNNER_LIBRARY`，**没有特性开关分化**。编译门控集中于 `core/tooling/config.h`，业务核心路径不存在因工具或调试特性引入的条件编译分支。

### F6 工具接缝的防腐（小、但值得先立规矩）

`core/tooling/` 是加进核心的 1,055 行。风险不是现状，而是"以后每来一类数据都往里加一个专属钩子"，那它就会变成第二个核心。

**核心防腐规则**：
- **数据源是枚举（Snapshot），不是每个数据源一个钩子**；
- **能力位显式声明，业务策略留在模块**；
- 核心只保留通用只读接缝（`elementRoots()`、`findElement(id)`、`setAfterCompose(cb)`、`requestElementRefresh()`），不感知属性表、补丁存储与虚拟化树快照。`grep -rn "ElementField\|ElementPatch\|ElementValues" core include` 必须保持为 0。

## 三、已知技术债复核

对历史记录中的技术债进行复核，明确现状与处理原则：

| 历史事项 | 现状与结论 |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `openWindow` 返回值 `void → DslWindowHandle`（ABI 兼容性） | **已实施**：`include/eui/app.h` 与 `dsl_app_impl.h` 已返回 `DslWindowHandle`。相关用法已同步到 `docs/DSL.md`。                      |
| GLFW 主循环 wait-timeout 与"静止时 wait events"是否冲突    | **无冲突**：`glfwWaitEventsTimeout` 仅用于托盘隐藏（0.10s）与最小化（0.25s）的必要轮询；普通空闲状态严格走 `waitForEvents` 休眠。 |
| 文本 ink-box 居中对齐差异（含降部字符标签基线偏高）        | **机制确认**：`core/render/text.cpp` 的 `VerticalAlign::Center` 采用实际字形物理墨水框上下界居中，导致含降部字符（如 `p`、`y`）的单词相较纯基线字符单词视觉偏高，属排版度量机制特性，待未来统一基线度量规范。 |

## 四、建议顺序

| 顺序 | 内容                                                          | 风险 | 价值   |
| ---- | ------------------------------------------------------------- | ---- | ------ |
| 1    | **F1-A1/A2**：框架外目录改走公开包含路径 + 落自动化检查       | 低   | 最高   |
| 2    | **F2**：`Runtime` 类头按域分节（零行为改动）                  | 低   | 中     |
| 3    | **F6**：遵守工具接缝防腐规则（保持协议统一）                  | 无   | 防未来 |
| 4    | F3 / F4：按痛点决定拆不拆                                     | 中   | 中低   |
| —    | 需要拍板：是否把 `eui/*` 提升为受版本约束的公共 API（决定要不要做名字迁移） | —    | —      |

## 五、明确不做

- **不动 `core/render` 的后端结构**（Vulkan/OpenGL 已按目录分好，体量大不等于乱）。
- **不动布局与元素模型**：它们是框架的语义核心，改动风险与收益不成比例。
- **不为指标重构**：这次审计的唯一目的是"让维护者少花判断力"，不是为了行数变少。
