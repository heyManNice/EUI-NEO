# 工具协议（Tooling Protocol）

调试面板（`modules/devtools`）及其他外部工具（Profiler、HUD 等）需要观察框架内部状态：元素树、元素属性、命中结果、渲染变换、帧与性能数据，并且要能把这些值临时写回运行时。本文档规定了**框架工具接缝（Tooling Seam）的架构契约、职责边界与接入协议**。

核心目标是**让框架不再因为诊断工具而分化分支**：新增一类数据源（如 State / Input / Frames / Layout / Animations / Resources / Windows / Scale 等标签页）应该只需要工具侧实现展示逻辑，而不需要在核心文件中反复插入条件编译。

## 一、核心原则

1. **能力归核心，策略归模块**：
   - **核心拥有的能力**：把元素树根节点交出、按 ID 查找元素、计算几何与盒模型（Transform / Clip / Padding / Margin）、命中测试、性能快照、生命周期时机（Compose 之后、Layout 之前）。
   - **核心不感知的策略**：哪些属性可编辑、属性如何分组展示、树如何截断和虚拟化、高亮使用什么色带、是否有节点被“选中”、补丁的具体存储格式。
2. **复杂度留在读的人少的一侧**：
   - 框架核心代码会被每个贡献者高频阅读和维护，核心应尽可能精简、保持零分支与零虚函数膨胀；
   - 工具模块属于选择性启用的调试功能，多承担数据编排、拷贝节流和状态管理是合理的架构权衡。
3. **Release 构建零开销与符号零残留**：
   - 工具接缝通过独立开关 `EUI_TOOLING` 控制；
   - 未开启工具接缝时，核心钩子全部内联为空操作（No-op inline），`Runtime` 内部仅存一个空指针（8 字节），生产构建中不包含任何工具符号和模块二进制。

## 二、协议模型

协议抽象为三个动词与一个帧驱动模型：

```text
Snapshot   枚举指定数据源（元素树、状态实例、事件流、重绘原因、动画、资源、窗口度量）
Resolve    按 ID 查询几何（Frame / Transform / Clip / 盒模型）、命中测试、版本号
Control    临时覆写字段（Patch / Clear）、请求重绘 / 重排 / 重组、开关性能采样
Frame      宿主每帧驱动：beginFrame(dt, metrics) -> present
```

工具接缝的数据源映射：

| 领域 / 标签页      | 数据源类别   | 核心接口需求                                      |
| ------------------ | ------------ | ------------------------------------------------- |
| Elements / Layout  | Elements     | `elementRoots()`、`findElement(id)`、盒模型计算   |
| Performance        | Metrics      | `PerformanceSnapshot` 性能度量                    |
| State              | Instances    | `InstanceStore` 实例表只读枚举                    |
| Input              | Events       | 最近事件环形队列采样与命中路由                    |
| Frames             | FrameReasons | 重绘触发原因计数                                  |
| Animations         | Transitions  | 活跃过渡动画与计时器状态                          |
| Resources          | Resources    | 字体、纹理缓存条目与内存开销                      |
| Windows            | Windows      | 多窗口与 Modal 状态                               |
| Scale              | Metrics      | DPI / PointerScale / UIScale                      |

## 四、生命周期时序与钩子

核心在执行流程中仅调用无条件内联钩子，不包含具体的业务分支：

```text
页面更新阶段：
  tooling::beforeCompose(runtime)     -> 世代计数自增，缓存路径失效
  composeFn(ui, screen)               -> 应用代码构建新元素树
  ui.end()
  tooling::afterCompose(runtime)      -> 触发工具注册的补丁回放（在 Layout 之前写回活元素）
  ui.layout(...)                      -> 执行几何测量与布局排版

渲染阶段：
  页面普通渲染...
  tooling::drawPassOverlay(...)       -> 传递 RenderPassContext，工具在同一裁剪空间下填充预览
  tooling::drawOverlay(...)           -> 独立图层覆盖绘制（例如停靠面板自身）
```

- **`afterCompose` 回调机制**：核心只提供“树刚生成完毕、布局尚未发生”的时机。工具将自己的补丁应用逻辑（如 `ElementPatches::apply(page)`）挂载在该钩子上，使临时覆盖的属性随新树一同生效，且不污染应用源状态。
- **输入过滤机制**：工具通过 `Runtime::setInputFilter` 接管命中测试指针，使元素拾取（Picker）操作优先被工具消费，而不触发页面的点击事件。

## 五、属性字段表驱动规范（X-Macro）

为保证属性扩展的高可维护性，字段映射完全收敛在 `modules/devtools/devtools_fields.h`：

```cpp
#define DEVTOOLS_ELEMENT_FIELD_TABLE(X)               \
    X(Color,           Color,  color)                 \
    X(Opacity,         Number, opacity)               \
    X(Radius,          Number, radius)                \
    X(BorderWidth,     Number, border.width)          \
    ...
```

- **扩展一个可编辑属性的流程**：
  1. 在 `devtools_fields.h` 的 `DEVTOOLS_ELEMENT_FIELD_TABLE` 增加一行（字段名、数据类型、Element 结构体成员）；
  2. 在 `devtools_properties.cpp` 的 `propertyDescriptors()` 增加一行展示元数据（标签名称、数值范围、适用的元素类型）；
  3. **核心代码 0 行修改**：读值、写值、类型校验、补丁存储及 UI 控件分发均由宏表自动展开。

## 六、架构不变量与验证方式

所有改动必须满足以下架构不变量：

```bash
# 1. 核心与公共头中不包含工具门控宏（仅限 core/tooling/config.h）
grep -rn "EUI_DEBUG_BUILD" core include CMakeLists.txt
# 期望：除 config.h 声明及 CMake 默认开关外为 0 行

# 2. 核心运行时中不存在工具字段标识
grep -rn "ElementField\|ElementPatch\|ElementValues\|FieldValue" core include
# 期望：0 行

# 3. 核心代码中不存在具体字段分支
grep -rn "ElementField::" core include
# 期望：0 行

# 4. Release 构建不导出工具符号
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release --target eui_neo
llvm-nm --defined-only build-release/lib*eui_neo*.a | grep -cE "DevtoolsHost|ElementPatches"
# 期望：0

# 5. 单元测试与端到端验证覆盖
ctest --test-dir build -R "devtools|runtime_inspection|runtime_viewport" --output-on-failure
```

## 七、扩展规则与反模式

### 核心公开面的增长约束
1. **只传递计算结果，不暴露内部容器**：如果工具需要了解布局或测量结果，核心应计算完毕后以只读结构交付（如 `RenderPassContext`），严禁将核心内部的 `std::vector`、`std::unordered_map` 等实现容器直接暴露给工具层。
2. **单一数据流**：工具面板直接通过当前绑定的页面 `Runtime` 接口进行单向读取与时机注册，不建立多层虚代理转发。

### 明确不做的反模式
- **禁止为单一面板定制核心回调**：新需求必须收敛在通用数据源（Snapshot）或统一几何解析（Resolve）之中。
- **禁止在核心层实现字符串反射**：保持静态编译期元编程，不为 Element 引入动态虚派发和运行时字典寻址。
- **禁止工具代码污染 Release 发行版**：工具状态与实现只能存在于 `modules/devtools` 动态/静态库内，关闭 `EUI_TOOLING` 的发行包必须保持零开销。
