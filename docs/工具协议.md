# 工具协议（Tooling Protocol）

调试面板（`modules/devtools`）需要读到框架内部的东西：元素树、元素属性、命中结果、渲染变换、帧与性能数据，并且要能把这些值临时写回去。本文写的是**框架该以什么形状提供这些能力**，以及把现有实现迁移过去的分步计划。

目标不是"让 devtools 更优雅"，而是**让框架不再因为工具而长分支**：新增一类数据源（计划中的 State / Input / Frames / Layout / Animations / Resources / Windows / Scale 八个标签页）应该只需要工具侧写代码，而不是再往核心文件里插一个 `#if`。

## 现状与度量

| 指标 | 数值 |
| --- | --- |
| 模块规模 | 15 个文件、约 2965 行 |
| 相对 `main` 的框架改动 | 19 个文件、+1879 / −137 行 |
| `core/` + `include/` 中 `EUI_DEBUG_BUILD` 出现次数 | 42 次，散在 12 个文件（`main` 上只有 1 次） |
| 最重的文件 | `runtime_lifecycle.h`(14)、`dsl_app_impl.h`(8)、`dsl_runtime.h`(5)、`runtime_instances.h`(4) |

`main` 上唯一那处是 `dsl_app.h` 里 `showDebugStatsInTitle` / `showDebugOverlay` 的默认值，属于"开发构建的便利开关"，不是工具协议的一部分。

## 根因：核心在替工具回答"策略"

现在核心里的东西可以分成两类，混在一起了：

- **能力（核心应该拥有）**：把元素树拷出来、按 id 找元素、算一个元素的 transform / clip / 盒模型、命中测试、性能快照、结构变更计数、覆写值的应用时机（compose 之后、layout 之前）。
- **策略（核心不该知道）**：哪些属性存在（`DebugPropertyId` 定义在 `core/runtime/runtime_inspector.h`）、属性怎么分组展示、树怎么给面板用、拾取器是什么、悬浮高亮用什么颜色（`kInspectionHoverPalette` 在核心）、"选中元素"这个概念。

`DebugPropertyId` 是最典型的一例：**"面板能改哪些字段"是工具的编辑决定，却定义在核心里**，所以每加一个属性都要同时改核心的枚举、两个 setter 和 `applyDebugOverride`。`Runtime` 上的 15 个工具方法（`elementTree` / `setDebugElementOverride` / `debugElementProperties` / `debugElementAt` / `setOverlayRenderer` / `pushPointerEvent` …）和 `InstanceStore` 里的 4 个工具成员是同一问题的另一种表现。

## 协议形状

三个动词 + 一个数据模型，工具只 include 一个头：

```
Snapshot   枚举某个数据源（元素、实例、事件、帧原因、动画、资源、窗口、度量）
Resolve    按 id 取几何（frame / transform / clip / 盒模型）、命中测试、取度量、读版本号
Control    写字段（patch / clear）、请求重绘 / 重排 / 重组、开关采样
Frame      框架每帧驱动：beginFrame(dt, metrics) → present
```

关键是 **Snapshot 是"枚举"而不是"八套定制钩子"**：计划中的八个标签页全都是"把某类 X 列出来"，所以协议只需要一个枚举能力加八个数据源。

工具侧的落点：

| 计划中的页 | 数据源 | 今天需要改核心吗 |
| --- | --- | --- |
| Elements / Layout | Elements（元素树，含 frame） | 否（已有） |
| Performance | Metrics（性能快照） | 否（已有） |
| State | Instances（实例库按 id 枚举） | 加一个数据源，不改调用点 |
| Input | Events（最近 N 个事件 + 路由结果，可开关采样） | 同上 |
| Frames | FrameReasons（重绘原因计数） | 同上 |
| Animations | Transitions / Timers | 同上 |
| Resources | Resources（字体、图片缓存条目） | 同上 |
| Windows | Windows（窗口与 modal 状态） | 同上 |
| Scale | Metrics（dpi / pointerScale / uiScale） | 否 |

## 文件与职责（目标形态）

| 文件 | 职责 | 状态 |
| --- | --- | --- |
| `core/tooling/config.h` | `EUI_TOOLING` / `EUI_DEBUG_BUILD` → `EUI_TOOLING_ENABLED` / `EUI_DEV_BUILD`，**全仓唯一的门控判定** | ✅ 已建 |
| `core/tooling/model.h` | 元素树快照、元素值、字段读写（由 `core/runtime/runtime_inspector.h` 迁入） | ✅ 已迁 |
| `core/tooling/inspect.h` | 元素查找、覆写提交、盒模型解析与预览几何（由 `core/runtime/runtime_inspection.h` 迁入） | ✅ 已迁 |
| `core/tooling/state.h` | `ToolingState`：所有工具状态（覆写表、悬浮标记、overlay 原语、compose 世代、输入过滤器、宿主事件队列、overlay 渲染器）都在这一块，由 `Runtime` 持有一个指针；工具未接入时它是空结构体 | ✅ 已建 |
| `core/tooling/hooks.h` | 核心调用的钩子与工具入口：`beforeCompose` / `afterCompose` / `resetHostInput` / `mergeHostInput` / `filterInput` / `drawOverlay` / `releaseGraphics` / `release`，以及 `ensureTooling` / `applyToolPatches` / 四个接入入口。工具关闭时每个钩子是空内联，并且工具 API 仍有无副作用的定义（协议在所有配置都存在，只是不生效） | ✅ 已建 |
| `include/eui/tooling.h` | 公开接缝：工具注册表、`Tool` 接口、版本与能力位 | ⏳ 阶段 4 |

阶段 1b 之后，核心侧只剩**一行钩子调用**，且不再需要条件编译。例如 `runtime_lifecycle.h` 的 compose：

```cpp
tooling::beforeCompose(*this);      // 世代自增、缓存路径失效
composeFn(ui_, screen);
ui_.end();
applyToolPatches();                 // 把工具的补丁写回新树（layout 之前）
ui_.layout(...);
```

`applyToolPatches()` 是 `Runtime` 的成员（它需要拿到 `ui_`），其余钩子只需要公开的 `Runtime::tooling()`，所以是自由函数。Release 下这些钩子是空内联，`Runtime` 只多一个 `std::unique_ptr<ToolingState>`（8 字节，工具不注册就永远为空），面板实现与工具状态都不进 Release。

## 验收与不变量

阶段 1b 之后成立：

```bash
# 1. 框架不再按“是不是调试构建”分支：门控只在 config.h 判定
#    期望：core/tooling/config.h（加 CMake 一行），其余位置 0 处
grep -rn "EUI_DEBUG_BUILD" core include CMakeLists.txt

# 2. 运行时不再关心工具：门控只应出现在接缝与一处预览绘制里
grep -rn "EUI_TOOLING_ENABLED" core include

# 3. Release 里没有工具：符号为 0，工具状态永远不会被实例化
llvm-nm --defined-only build-release/eui_neo.lib | grep -c -E "findDebugElement|applyDebugOverride|computeInspection|ToolingState"

# 4. 行为护栏
ctest --test-dir build -L unit
```

第 4 条里 `devtools_host`（面板状态机/输入路由/停靠/拾取）、`runtime_debug_properties`（覆写往返）、`element_property_bridge`、`runtime_inspection`、`element_tree` 五个用例是迁移的主要护栏；`image_stream` 与 `pointer_input` 是既有的、与工具无关的失败。

唯一剩下的核心分支在 `runtime_render.h`：悬浮预览必须在**页面渲染过程中**画出（靠渲染器自己的 scissor 状态保持裁剪），所以它的声明、调用点与定义带门控。阶段 3 把盒模型色带与预览绘制搬回模块后会一起消失。

## 六、分阶段

| 阶段 | 内容 | 完成标志 |
| --- | --- | --- |
| **1a 门控与位置**（已完成） | 建 `core/tooling/`：`config.h` 做唯一门控；`runtime_inspector.h` / `runtime_inspection.h` 迁为 `model.h` / `inspect.h` 并把门控改用 `EUI_TOOLING_ENABLED` | `core` + `include` 中 `EUI_DEBUG_BUILD` 只在 `config.h`（加上 CMake 一行）；行为与测试不变 |
| **1b 状态与钩子**（已完成） | `ToolingState` 收拢 `InstanceStore` 与 `Runtime` 里的工具状态；`hooks.h` 提供钩子与入口；`RuntimeRenderer` 改拿 `ToolingState*`；元素查找与树快照移到工具层；工具 API 在所有配置都有定义（关闭时无副作用） | 核心运行时文件里只剩 `runtime_render.h` 一处预览绘制分支（见下）；两种配置都零工具符号 |
| **1c 应用层桥** | `dsl_app_impl.h` 里那组 publish/apply 与 overlay 接驳（8 处）搬进 `core/tooling/app_bridge.h`，应用循环改成无条件调桥 | `include/` 里不再有工具分支 |
| **2 挪策略** | `DebugPropertyId` → 字段表（X-macro），核心只做“读字段/写字段”，标签、范围、编辑器类型留在模块；`DebugElementOverride` → 通用 patch；同时把 `Debug*` 命名改为中性命名 | 核心不再出现“属性”这个概念；加一个可编辑属性 = 核心数据 1 行 + 模块 1 行 |
| **3 挪 UI** | 盒模型色带、悬浮预览配色与绘制 → 模块；核心只留 `Resolve`（transform / clip / 盒模型解析） | 核心的 `Inspection` 只剩几何 |
| **4 协议化** | `eui/tooling.h` 定稿：版本号 + 能力位、多工具注册表（取代单实例 `setOverlayHost`）、`Tool` 接口与 overlay 宿主分离；模块的面板源改跟 `EUI_TOOLING` 而不是 Debug 配置 | **不改核心即可实现第二个客户端**（headless 导出工具或 CLI） |
| **5（可选）** | 传输层抽象：进程内函数表 → 本地 socket / JSON；面板降为"客户端之一" | 外部前端（浏览器 devtools 前端、编辑器面板）可连 |

## 明确不做

- **不做运行时反射**：字段表必须是编译期的，不引入字符串字段名与每元素虚派发。
- **不提前做 IPC**：数据模型按"可序列化"设计（纯结构体、无指针），传输留到阶段 5 有第二个客户端时再说。
- **不做万能钩子**：协议只有三个动词，新需求必须落进某个数据源；否则只是把 42 个点换个名字。
- **不一次铺开**：每个阶段独立可发布、可回滚；阶段 2 是唯一会碰覆写语义的一步，单独做并靠 `runtime_debug_properties` 的往返用例兜住。
