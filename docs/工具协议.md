# 工具协议（Tooling Protocol）

调试面板（`modules/devtools`）需要读到框架内部的东西：元素树、元素属性、命中结果、渲染变换、帧与性能数据，并且要能把这些值临时写回去。本文写的是**框架该以什么形状提供这些能力**，以及把现有实现迁移过去的分步计划。

目标不是"让 devtools 更优雅"，而是**让框架不再因为工具而长分支**：新增一类数据源（计划中的 State / Input / Frames / Layout / Animations / Resources / Windows / Scale 八个标签页）应该只需要工具侧写代码，而不是再往核心文件里插一个 `#if`。

## 现状与度量

| 指标 | 数值 |
| --- | --- |
| 模块规模 | 15 个文件、约 2965 行 |
| 相对 `main` 的框架改动 | 19 个文件、+1879 / −137 行 |
| `core/` + `include/` 中 `EUI_DEBUG_BUILD` 出现次数 | 42 次，散在 12 个文件（`main` 上只有 1 次） |
| 最重的文件 | `runtime_lifecycle.h`(14)、`dsl_app_impl.h`(8)、`dsl_runtime.h`(5)、`runtime_instances.h`(4) |

`main` 上唯一那处是 `dsl_app.h` 里 `showDebugStatsInTitle` / `showDebugOverlay` 的默认值，属于"开发构建的便利开关"，不是工具协议的一部分。

## 根因：核心在替工具回答"策略"

现在核心里的东西可以分成两类，混在一起了：

- **能力（核心应该拥有）**：把元素树拷出来、按 id 找元素、算一个元素的 transform / clip / 盒模型、命中测试、性能快照、结构变更计数、覆写值的应用时机（compose 之后、layout 之前）。
- **策略（核心不该知道）**：哪些属性存在、属性怎么分组展示、树怎么给面板用、 拾取器是什么、悬浮高亮用什么颜色、"选中元素"这个概念。（前三项已在阶段 2/3 完成，这一节记的是改造前的样子。）

阶段 2 之前，`DebugPropertyId` 是最典型的一例：**"面板能改哪些字段"是工具的编辑 决定，却定义在核心里**，每加一个属性都要同时改核心的枚举、两个 setter 和 `applyDebugOverride`。`Runtime` 上的 15 个工具方法（`elementTree` / `setDebugElementOverride` / `debugElementProperties` / `debugElementAt` / `setOverlayRenderer` / `pushPointerEvent` …）和 `InstanceStore` 里的 4 个工具成员是同一问题的另一种表现。阶段 2 把字段表化成一表一行，阶段 3d 又把它整个搬进模块，现在核心只剩"把元素树给工具看、让工具找/写一个元素、告诉它什么时候写"四个通用入口，枚举、三个 setter、`applyDebugOverride`、字段表、补丁存储全部离开了核心。

## 协议形状

三个动词 + 一个数据模型，工具只 include 一个头：

```
Snapshot   枚举某个数据源（元素、实例、事件、帧原因、动画、资源、窗口、度量）
Resolve    按 id 取几何（frame / transform / clip / 盒模型）、命中测试、取度量、读版本号
Control    写字段（patch / clear）、请求重绘 / 重排 / 重组、开关采样
Frame      框架每帧驱动：beginFrame(dt, metrics) → present
```

关键是 **Snapshot 是"枚举"而不是"八套定制钩子"**：计划中的八个标签页全都是"把某类 X 列出来"，所以协议只需要一个枚举能力加八个数据源。

工具侧的落点：

| 计划中的页 | 数据源 | 今天需要改核心吗 |
| --- | --- | --- |
| Elements / Layout | Elements（元素树，含 frame） | 否（已有） |
| Performance | Metrics（性能快照） | 否（已有） |
| State | Instances（实例库按 id 枚举） | 加一个数据源，不改调用点 |
| Input | Events（最近 N 个事件 + 路由结果，可开关采样） | 同上 |
| Frames | FrameReasons（重绘原因计数） | 同上 |
| Animations | Transitions / Timers | 同上 |
| Resources | Resources（字体、图片缓存条目） | 同上 |
| Windows | Windows（窗口与 modal 状态） | 同上 |
| Scale | Metrics（dpi / pointerScale / uiScale） | 否 |

阶段 1b 之后，核心侧只剩**一行钩子调用**，且不再需要条件编译。例如 `runtime_lifecycle.h` 的 compose：

```cpp
tooling::beforeCompose(*this);      // 世代自增、缓存路径失效
composeFn(ui_, screen);
ui_.end();
tooling::afterCompose(*this);       // 工具把自己写的值放回刚组好的树（layout 之前）
ui_.layout(...);
```

`afterCompose` 是纯粹的"时机"：核心不说那里该发生什么，工具要这一刻就在 `setAfterCompose` 里注册自己的回调（面板把 `ElementPatches::apply(page)` 挂在上面，于是它写的值在每棵新树 layout 之前回到元素上）。其余钩子只需要公开的 `Runtime::tooling()`，所以是自由函数。Release 下这些钩子是空内联，`Runtime` 只多一个 `std::unique_ptr<ToolingState>`（8 字节，工具不注册就永远为空），面板实现与工具状态都不进 Release。

## 验收与不变量

阶段 1c 之后成立（`1c` 的入口也在这个文件，是 `include/` 里唯一还有门控的文件）：

```bash
# 1. 框架不再按“是不是调试构建”分支：门控只在 config.h 判定
#    期望：core/tooling/config.h（加 CMake 一行），其余位置 0 处
grep -rn "EUI_DEBUG_BUILD" core include CMakeLists.txt

# 2. 运行时不再关心工具：门控只应出现在接缝与两处开发便利里
#    期望（3b 后共 2 处）：core/app/app_runner.h 1、include/eui/dsl_app.h 1（均为开发构建便利）
#      接缝自己（overlay_hooks.h）不需要门控：它只是一组函数槽，没人填就是空
grep -rn "EUI_TOOLING_ENABLED" core include

# 2b. 核心运行时里一处都不剩（原本最重的文件是 runtime_lifecycle.h 14 处、runtime_render.h 3 处）
#     期望：0 行
grep -rn "EUI_TOOLING_ENABLED" core/runtime core/input core/render core/app/performance_snapshot.h

# 3. Release 里没有工具：符号为 0，工具状态永远不会被实例化
llvm-nm --defined-only build-release/eui_neo.lib | grep -c -E "findElement|applyElementPatch|computeInspection|ToolingState|ElementPatch"

# 4. 行为护栏
ctest --test-dir build -L unit
```

第 4 条里 `devtools_host`（面板状态机/输入路由/停靠/拾取，含一个接到真实页面上的端到端段）、`devtools_fields`（字段表、补丁存储与"写完活元素"往返）、`devtools_tree`（树快照）三个用例是迁移的主要护栏；`runtime_inspection` 仍守住核心的几何与拾取，`image_stream` 与 `pointer_input` 是既有的、与工具无关的失败。

阶段 2 之后成立：

```bash
# 5. 核心不再有"属性"这个概念：没有属性枚举、没有按属性分支的 setter
#    期望：0 行（字段表的行名是本框架自己的字段，不是工具的属性名）
grep -rn "DebugProperty" core include

# 5b. 核心也不再知道"可写字段"这件事：字段表、元素值与补丁都在工具里
#     期望：0 行

grep -c "^    X(" modules/devtools/devtools_fields.h   # 17 个字段 + 7 条"需要开关" = 24

# 7. 核心没有一处按字段名分支：字段名根本不在核心里
#    期望：0 行
grep -rn "ElementField::[A-Z]" core include

```

应用层同理：`dsl_app_impl.h` 里的 8 处接驳搬进桥之后，它自己不再出现任何工具分支（`grep -c EUI_TOOLING_ENABLED include/eui/detail/dsl_app_impl.h` 为 0），`DslAppState` 也不再含工具字段——这份状态现在归桥所有。

阶段 3 之前有一处例外的核心分支在 `runtime_render.h`：悬浮预览必须在**页面渲染过程中**画出（靠渲染器自己的 scissor 状态保持裁剪），所以它的声明、调用点与定义带门控。现在这一处也不再是分支：渲染过程本身成了接缝的一环——`tooling::drawPassOverlay(ui, instances, tooling_, backend, ...)` 是一行无条件调用，工具关掉时它是空内联，没有工具接入时它解析几何之前就返回（`core/tooling/pass.h` 的 `RenderPassContext` 把后端与解析好的几何一起交给工具）。预览的调色板、色带与绘制现在全在 `modules/devtools/devtools_preview.cpp`。

## 判断标准：复杂度放在读的人少的一侧

这个接缝的每一个形状决定都用同一条尺子量：

- **框架代码每个贡献者都会读**，而且会被上游反复审；工具模块只有做工具的人读，而且是 opt-in、Debug-only。所以**复杂度应该待在读的人少的那一侧**：核心少一层接口、少一套状态；工具多知道一点框架（它要 include 页面 Runtime、自己维护节流）——这笔交易划算。
- **一件事只在一处**。数据流现在是“模块 → Runtime”一条直路；面板要什么、什么时候要、写回什么，全在模块的一个 `frame()` 里，读者不需要在三个文件之间拼。
- **每个概念都属于需要它的人**：核心只拥有能力（几何解析、帧内时机、输入/绘制钩子），应用层只拥有窗口与帧，工具拥有策略与它自己的状态。

三条反模式（新需求可以拿它们直接判）：

1. 每来一类数据就往核心加一个专属钩子——数据源应该是枚举（Snapshot），不是一堆钩子；
2. 把“显示什么 / 怎么编辑”的决定留在核心——那是工具的编辑决定；
3. 让工具绕过接缝去改核心内部——那会让核心重新长出 `#if`。

## 明确不做

- **不做运行时反射**：字段表必须是编译期的，不引入字符串字段名与每元素虚派发。
- **不提前做 IPC**：数据模型按"可序列化"设计（纯结构体、无指针），传输留到阶段 5 有第二个客户端时再说。
- **不做万能钩子**：协议只有三个动词，新需求必须落进某个数据源；否则只是把 42 个点换个名字。
- **不一次铺开**：每个阶段独立可发布、可回滚；阶段 2 是唯一会碰覆写语义的一步，单独做并靠 `element_patch` 的字段往返用例兜住（已完成）。
